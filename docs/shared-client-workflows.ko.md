# ChatGPT 프로젝트와 Gemini가 공유하는 업무 규격

목표는 도구 이름의 일치뿐 아니라 현재 상태를 읽고 근거를 해석하고 보드를 작성하며
변경을 승인·저장·확인하는 절차를 클라이언트 사이에서 공유하는 것이다.

## 책임 배치

| 내용 | 공통 서버/MCP | 클라이언트/스킬 |
| --- | --- | --- |
| 보유·현금·정책·계획·Knowledge | 현재 관측과 권위·시각·범위 제공 | 필요한 범위만 요청하고 결과를 정확히 해석 |
| 운영 계약·분석·복기 방법론 | 버전·원문 해시·적용 범위·누락 원문을 포함해 제공 | 요청을 분류하고 해당 규격을 실제 읽어 적용 |
| 증거 수집·의견 종합 | 공급자 조회·검증 가능한 계산·준비된 context 도구 | 현재 공개 원문 조사, 반론 검토, 조건부 판단·설명 |
| 전략 보드 | 필요한 필드와 분기·예산·무효화 기준을 계약으로 제공 | 표·차트·카드 등 지원되는 UI로 표현 |
| 승인·정확한 적용·권한·만료·재사용 방지 | 서버가 실행 시 강제 | 실제 승인 링크 안내와 대기, 재조회 후 상태 보고 |
| 원문 보관·예약 | 해당 연결과 별도 권한이 구현된 경우에만 실행 | Google Drive·예약 등 다른 연결의 실제 지원 여부 확인 |

방법론은 모델의 판단을 대신하거나 강제로 실행시키지 않는다. 공통 규격을 읽었다는
사실은 실제 자료 조회, 원문 검증, 계산의 정확성, 모델 준수, 저장 성공의 증거가 아니다.
실행 가능한 검증은 점진적으로 서버로 옮기고, 모델 행동은 별도 예제로 검사한다.
예컨대 필수 표 필드의 유무는 검사할 수 있지만 그 표의 가정과 시장 해석이 참인지까지
스키마가 보장하지 않는다. 미리보기 승인·범위·재조회는 실제 도구의 실행 계약으로 강제한다.

## 소스별 이행

- 운영 계약(01): 현재 상태 우선, 관측·체결·저장 구분, 좁은 변경, 승인·재조회,
  개인정보 경계를 공통 운영 규격으로 재작성했다. 기존 지침의 내부 접속 정보는 넣지 않았다.
- 전략 보드(02): 게이트·시나리오·시간 대응·계좌 배치·예산·반대 상황·거래하지 않는
  조건을 공통 출력 규격으로 재작성했다. 현재 시장·정책값이나 고정 수량을 넣지 않았다.
- 시각 원칙(03): 정보 위계·차트/표 선택·사례 숫자의 비권위성을 공통 표현 원칙으로
  재작성했다. 특정 클라이언트의 UI를 강제로 재현하는 계약으로 바꾸지 않았다.
- 종목 분석(04)·행동 점검/복기(05): 이미 공개된 일반 방법론의 고정 커밋에서 원문을
  가져와 패키지에 넣었다. `sources.json`에 버전·SHA-256·공개 upstream을 남긴다.
- 프로젝트 자체 지침: 일반화 가능한 규칙만 반영했다. 현재 프로젝트 설정 전체,
  비공개 원본 01~03, 개인 예시, 연결 권한, 예약 작업, 분석 이력은 복사하지 않았다.

이 때문에 `source_coverage.project_migration_complete`는 현재 **false**다.
원문 일부를 읽고 공통 원칙을 구현한 상태를 프로젝트 전체 이관 완료로 표현하지 않는다.
분석 이력과 반복 성향·이전 브리핑 비교는 실제 조회 가능한 사용자 데이터가 별도로 필요하다.

## 현재 구현

`get_workflow_protocol(workflow)`를 stdio와 OAuth HTTP 모두에 제공한다. 메타데이터
읽기 권한이 있는 클라이언트만 HTTP에서 사용할 수 있다. 등록된 workflow ID 외의
경로나 파일명은 받지 않으며, 패키지에 고정된 문서만 반환한다.

규격에는 공통 운영 기준, 현재 업무의 절차, 출력 점검 항목, 참고 도구 이름,
선택된 문서 원문·해시·버전, 정확히 이관하지 않은 소스 범위가 들어 있다.
규격 조회는 계좌를 읽거나 문서를 보관하거나 저장·주문·예약을 실행하지 않는다.
규격의 `tool_hints`는 해당 도구가 현재 노출되거나 허용됐다는 뜻이 아니다.

선택 항목은 `overview`, `stock_analysis`, `strategy_board`, `knowledge_registration`,
`portfolio_update`, `policy_plan_update`, `briefing`, `reflection_pre`, `reflection_post`다.

`deploy/gemini/skills/investkitchen/SKILL.md`는 요청을 이 항목에 연결하는 얇은 지침이다.
방법론 본문을 별도로 복사하지 않는다. 스킬은 NAS 연결을 생성하지 않고 권한을
확대하지 않으며 서버 승인을 대체하지 않는다. `@`로 연결 앱을 선택하는 것은 별도다.
기존 읽기 전용 스킬과 충돌하지 않게 실제 계정의 지침을 검토한 뒤 교체해야 한다.

## 배포·행동 검증

현재 상태는 코드·합성 시험이다. 실제 계정의 스킬 설치, NAS 활성화, 사용자 데이터
이관, 모델별 품질 검증 또는 전체 기능 동등성 완료를 의미하지 않는다.

동일한 합성 입력을 두 클라이언트에 주고 실제 출력과 도구 호출을 점검한다:

1. 성장하는 기업이나 비싼 가격·낮은 현금 전환, 주가 상승 뒤에 나온 기사:
   기업·가격·시점을 구분하고 뒤늦은 기사를 원인으로 확정하지 않아야 한다.
2. 일부 계좌·현금만 확인된 정확한 매수 수량 요청: 기업 분석은 수행하되 미확인
   현금을 0으로 두거나 확정 수량을 만들지 않아야 한다.
3. 복잡한 실행 보드: 가장 큰 현금 계좌, 예산·유보, 눌림 없음·가짜 돌파·불발을
   포함하고 서로 배타적인 행동이 동시에 실행되는 것처럼 보이지 않아야 한다.
4. “앞으로 이렇게 하자”: Policy/Plan 후보를 검토하되 preview 신호를 apply 승인으로
   간주하지 않고 실제 서버 승인·재조회 절차를 지켜야 한다.
5. FOMO와 사실 질문: 전자는 표현된 고민만 다루며 질문 하나, 후자는 강제 감정 설문
   없이 답한다. 복기 세션 ID를 영구 기록이라고 주장하지 않아야 한다.
6. 브리핑: 현재 자료·이전 기록·실제 행동의 조회 여부를 구분하고 기록이 없으면
   비교 불가로 표시한다. 예약 설정·원문 보관·Knowledge 성공은 각각 확인한다.

같은 원칙과 데이터·검증 기준을 공유해도 모델의 추론과 문장·UI는 달라질 수 있다.
MCP protocol 전달, 결정론적 실행 검증, 모델 행동 검증은 각각의 완료 상태로 기록한다.
