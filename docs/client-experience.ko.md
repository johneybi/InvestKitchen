# ChatGPT·Gemini에서 InvestKitchen 운영하기

2026-11-16 · 사용자 배포본 `2026-11-16.3` · 서버 방법론 `2026-11-16.2` · [이슈 #47](https://github.com/johneybi/InvestKitchen/issues/47)

이 문서는 사용자가 투자 대화에 넣는 지침·소스·스킬과 업데이트 방법을 정의한다.
개발용 Codex 스킬은 이 기능을 대신하지 않는다. 두 클라이언트 설치와 서버 배포는
별도로 확인했다. 실제 대화 검증은 부분 완료이며, Gemini 일반 채팅의 도구 실행과
다른 PC 검증을 포함한 전체 합격 판정은 아직 없다. 구체적인 모드별 결과는 #47에 기록한다.

## 무엇을 어디에 두는가

| 구성 | 제품 원본 | 실제 사용하는 곳 |
| --- | --- | --- |
| 투자 동료의 역할, 분석·개인 조언·PRE/POST·복합 질문·표현·저장 상태 | `client-instructions/core.ko.md` | 두 클라이언트의 주 지침에 공통 포함 |
| ChatGPT에서의 적용 범위·화면·연결 안내 | `client-instructions/chatgpt.ko.md` | 프로젝트 지침 뒤에 결합 |
| Gemini의 스킬·앱 선택·Canvas·연결 오류 안내 | `client-instructions/gemini.ko.md` | 사용자 스킬 뒤에 결합 |
| 운영 계약·전략 보드·표현·종목 분석·PRE/POST 상세 방법론 | `protocol/v1/workflows/sources/` | ChatGPT 소스 5개, Gemini 참고 파일 5개, MCP 방법론 |
| 현재 계좌·개인 Policy/Plan·Knowledge | InvestKitchen의 승인된 사용자 저장소 | 실제 MCP 조회·검증된 변경 |
| 개인의 말투/선호·비공개 아카이브 목적지 | 사용자의 비공개 설정 | 공통 제품 지침에 하드코딩하지 않음 |

주 지침 자체에 분석·코칭 방법을 넣는다. 상세 소스를 읽기 전에도 역할을 수행할 수
있고, 복합 요청에는 관련 상세 방법론을 함께 참조한다. 서버는 사실·권한·정확한 변경을
책임지고 웹 AI는 조사·추론·대화·화면 구성을 담당한다. MCP 설명문만 바꿔 모든 새 채팅에
지침이 자동 주입되거나 모델이 반드시 준수한다고 가정하지 않는다.

## ChatGPT 설치

1. 기존 프로젝트 지침과 소스를 비공개로 보관한다. 계좌·개인 선호와 공통 규칙을 구분한다.
2. [`project-instructions.ko.md`](../deploy/chatgpt/project-instructions.ko.md)의 본문을
   프로젝트 지침에 넣고, [`project-sources/`](../deploy/chatgpt/project-sources/)의 5개
   파일을 소스로 넣는다. 같은 역할의 오래된 01~05를 중복 적용하지 않도록 비교·교체한다.
   관련 없는 개인 자료를 지우지 않는다.
3. 해당 프로젝트에서 연결 앱이 실제 노출되는지 확인한다. 일반 채팅에 자동 전파되는
   설치로 간주하지 않는다. 프로젝트 밖에서도 쓸 환경은 지침 적용 경로를 별도로 정한다.
4. 새 채팅에서 설치 버전과 실제 방법론 버전을 확인하고 수용 시나리오를 수행한다.
   모델이 버전을 말하는 것만으로 설치 검증하지 않는다. 설정과 파일 목록도 대조한다.

필요한 비교·가정 탐색에는 현재 제공되는 시각화를 활용한다. 매번 인터랙티브 화면을
강요하지 않는다. 기능의 계정·플랫폼별 가용성과 생성 화면이 일반적으로 스냅샷이라는
점은 [공식 Visualizations 안내](https://learn.chatgpt.com/docs/visualizations)를 기준으로 한다.

## Gemini 설치

1. 기존 InvestKitchen 연결 앱의 연결 상태와 권한을 확인한다. 스킬 설치 때문에 정상
   OAuth 등록을 지우거나 새 연결을 만들 필요는 없다.
2. Customize → Skills에서 [`investkitchen/`](../deploy/gemini/skills/investkitchen/)
   폴더를 업로드하거나, 기존 스킬의 Replace skill로 같은 패키지를 교체한다. 기존 복사본은
   비공개 보관하고, 과거 `investkitchen-read`와 상충하는 중복 활성화를 정리한다.
3. 스킬이 활성 상태인지 확인한다. 패키지에는 `SKILL.md`, 참고 문서 5개, 버전 영수증이
   있다. 파일을 바꿀 때는 참고 문서를 포함한 전체 패키지를 교체한다.
   Replace skill 뒤 설치가 해제된 상태로 남을 수 있으므로, 저장 완료와 별도로
   Install/설치를 눌러 활성화하고 메뉴가 Uninstall/제거로 바뀌었는지 확인한다.
4. 새 일반 채팅의 `@` 메뉴에서 실제 InvestKitchen 연결 앱을 선택하고 자연어로 요청한다.
   스킬 자동 선택이 되지 않으면 화면에서 제공하는 `/` 또는 `@` 스킬 선택을 사용한다.
   자동 스킬 선택과 앱 도구 활성화는 별개다. 앱을 명시하는 사용을 기본 합격 경로로 둔다.
5. 동일 Google 계정의 다른 PC에서도 같은 새 채팅 시나리오를 반복한다. 계정 연결이
   보인다는 것만으로 교차 PC·모드 검증이 끝난 것은 아니다.

연결 앱 등록, Google 계정 링크, 채팅 도구 활성화, 스킬 설치는 별도로 확인한다.
Available actions에 도구가 보이거나 서버가 새 토큰을 발급했더라도 앱이 Connect/Add로
돌아오면 설치·연결 완료로 기록하지 않는다. 실제 새 채팅에서 도구 호출과 결과까지
확인한다. 토큰 원문 없이 동의·코드 교환 시각과 도구 호출 기록을 대조하며, 모델이
말한 Timeout/권한 없음/없는 도구를 실제 서버 오류로 채택하지 않는다.

Google은 SKILL.md·폴더·zip 업로드와 참고 파일을 포함한 교체를 안내한다.
**zip은 선택적인 묶음 형식**이며 별도의 실행 프로그램이 아니다. 스크립트로 NAS에
우회 접속하는 기능은 넣지 않는다. [공식 스킬 안내](https://support.google.com/gemini/answer/17094296?hl=en)

Gemini 일반 채팅의 목표 범위는 분석·계좌 조언·PRE/POST·허용된 저장이다. 현재 계정의
실제 비교에서는 앱을 선택한 Pro 일반 새 채팅이 실패했고, 같은 앱의 Pro Developer Mode에서는
상세 조회가 성공했다. 일반 채팅 실패 때 NAS는 인증과 도구 목록에 응답했지만 상세 도구
호출은 관측되지 않았다. 이 결과만으로 서버 결함이나 플랫폼 미지원이라고 단정하지 않는다.
후속 Developer Mode 요청도 도구 이벤트 없이 실패했고, 재연결에서는 NAS의 코드 교환과
접근·갱신 토큰 발급 이후에도 앱이 Connect/Add로 돌아오는 현상을 확인했다. 따라서 현재
남은 문제를 모델 선택만의 문제로 분류하지 않는다. Developer Mode의 한 번 성공을
일반 채팅·반복 호출·저장 성공으로 대체하지 않는다.

후속 확인에서는 같은 계정의 다른 PC도 Add/Connect 상태라는 사용자 보고와,
Developer Mode의 Authentication 화면에서 `No account linked`를 확인했다.
브라우저의 실제 Google `FinishOAuth` 응답은 HTTP 409와
`Malformed response cannot be parsed … for CODE_EXCHANGE`를 반환했고,
후속 `GetLink`는 404였다. 이는 모델이 추정한 오류가 아니라 계정 연결 완료 단계의
실제 응답이다. 토큰 교환 응답 처리까지 실패 범위를 좁히지만, 어느 응답 필드·HTTP
상태·중계 구간이 원인인지는 아직 확인하지 못했다. 성공적인 토큰 발급 이력과 별도로
후속 시도에서는 코드가 교환되지 않은 경우도 있어 모든 시도를 같은 결과로 묶지 않는다.
공개 토큰 주소의 무자격 오류가 정상 JSON이라는 검사도 실제 Google 코드 교환 성공의
증거가 아니다. 다음 진단은 같은 요청의 토큰 응답 상태·Content-Type·필수 필드의
존재와 자료형을 비밀값 없이 대조해야 한다. 원문 토큰·인증 코드·쿠키·HAR는 기록하지 않는다.

공식 맞춤 앱 안내의 지역·언어·계정·활동 설정 조건도 별도로 확인한다. 영어 화면으로
열었다는 사실은 계정의 모든 지원 조건 충족을 증명하지 않는다.
[Google 맞춤 앱 안내](https://support.google.com/gemini/answer/17209137?hl=en)

장기 연결 검증에는 최초 코드 교환뿐 아니라 접근 토큰 만료 뒤 갱신·반복 호출이 포함된다.
Google은 기존 갱신 토큰을 유지하는 Persistent Linking 방식을 안내하고, Authelia는
갱신 때 새 토큰을 발급하는 방식을 문서화한다. 이는 후속 비교가 필요한 호환성 차이며
현재 실패의 확정 원인은 아니다. 토큰 수명을 늘리거나 재사용 방어를 해제하는 변경을
단순 재연결 수리로 적용하지 않는다.
[Google OAuth 안내](https://developers.google.com/connected-apps/mcp/oauth),
[Authelia offline_access](https://www.authelia.com/integration/openid-connect/openid-connect-1.0-claims/)

Canvas는
문서·앱·시각 화면 구성에 활용할 수 있다. 다만 맞춤 MCP와 Canvas의 동시 사용은
실제 계정에서 따로 검증한다. 확인 전에는 도구가 보이는 일반 채팅에서 자료를 읽고,
Canvas에는 관측 시각을 붙인 최소 스냅샷을 사용한다. Canvas 자동 저장을 NAS 기록으로
보지 않는다. [공식 Canvas 안내](https://support.google.com/gemini/answer/16047321?hl=en)

현재 영구 Reflection 저장과 읽기, 지속 관찰·알림 전체 흐름은 별도 미완료 기능이다.
좋은 복기 대화가 가능하다는 사실을 이 저장 기능까지 구현됐다는 의미로 쓰지 않는다.
금융 데이터 공급자·개별 도구의 지원도 현재 MCP 노출과 권한으로 판정한다.

## 업데이트·버전 불일치·되돌리기

공통 원본 → 호스트별 생성 → 검사 → 기존 설치본 비교 → 두 계정 설치 → 새 채팅 검증
순서로 운영한다. 업로드본은 Git 변경을 자동 추적하지 않는다. NAS 배포와 업로드는
서로 다른 작업이다. `release.json`은 후보의 원본·산출물 해시를 기록하며 설치 증명이 아니다.

```sh
python3 scripts/build_client_instructions.py
python3 scripts/build_client_instructions.py --check
# 선택: 업로드할 zip. 생성된 산출물만 포함하며 개인 파일은 수집하지 않는다.
python3 scripts/build_client_instructions.py --zip dist/investkitchen-gemini.zip
```

실제 설치 기록에는 제품 커밋, 패키지 버전, 서버 방법론 버전, 설치 날짜·호스트·언어·모드,
활성 스킬/소스 목록, 수행 시나리오·결과를 비공개로 남긴다. 다른 버전이면 현재 실행
스키마·승인 계약을 우선하고 의미 충돌이 있는 변경만 보류한다. 읽기와 가능한 분석까지
전부 막지 않는다. 해결되지 않으면 이전 검증 패키지를 복원하고 새 패키지를 비활성화한다.
연결 앱·데이터·권한을 지우는 복구는 이 지침 교체에 포함되지 않는다.

HTTP 쓰기의 선택 설정 `approval_mode=approve_and_apply`는 정확한 변경을 NAS에서 검토한
사용자가 “이 변경 승인하고 저장”을 한 번 누르면 저장과 재조회를 수행한다. AI의 같은
apply 호출은 기존 결과를 반환하며 새로 저장하지 않는다. 원래 계정·권한·만료·CSRF·
승인 감사·정확한 후보 검증은 유지한다. 기본값 `approve_then_apply`는 기존 순서를 보존한다.
해당 설정은 운영에 전환됐으며 합성 시험을 통과했다. 실제 사용자의 한 번 승인부터
저장·재조회까지 이어지는 웹 검증 결과는 별도로 기록한다.

승인 기한은 실제 `approval_expires_at`을 사용한다. 원본 후보가 더 오래 유효해도 링크가
유효한 것으로 표시하지 않는다. 처리 결과는 같은 프로세스에서 최대 10분 보존하며,
재시작·응답 유실 뒤에는 원래 기록 ID/digest로 정본을 확인한다. 불확실한 변경을 다시
적용하지 않는다. 낮은 위험의 묶음 승인·상시 권한은 이 기능에 포함되지 않는다.

## 트레이딩 재료의 날짜

원문 게시일과 발행 대상일이 다를 수 있다. 예를 들어 토요일 게시 자료가 월요일을
다루면 Evidence의 `published_at`은 토요일로 보존하고, 실제 월요일용 재료 Claims의
`effective_at`은 확인된 월요일로 작성한다. `horizon`에 “월요일용”이라고 써도 서버는
자연어를 세션 권한으로 해석하지 않는다.

발행 요청을 함께 받은 Knowledge preview에는 지원되는 경우 `target_session_date`를
넣는다. 서버는 유효한 trading_material Claims의 적용일이 모두 대상일과 같은지 저장
전에 확인한다. JSON 문자열 연결에서도 이 값은 `update_json` 밖의 별도 인자다.
불일치는 후보를 만들지 않고 거절하며 게시 시각·Claims를 자동 변경하지 않는다.
대상일을 생략한 기존 지식 등록은 계속 동작하되 날짜 일치를 검증했다고 표시하지 않는다.

날짜가 맞아도 종목 검증, 근거 Claim 선택, SessionBrief 미리보기·승인·발행은 별도다.
`KRX:` 표기나 테마명이 자동 발행용 `asset:종목코드`와 같은 계약이라고 가정하지 않는다.
과거 발행일만 보일 때 최신 저장일과 실제 발행 결과를 따로 확인한다. 등록 성공을 발행
성공으로 보고하거나, 오래된 자료의 날짜만 오늘로 바꾸어 재사용하지 않는다.
