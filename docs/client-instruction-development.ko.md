# InvestKitchen 스킬과 지침 개발 운영 규칙

스킬과 프로젝트 지침은 제품 소스로 관리한다. 기능을 바꾸면 서버 동작뿐 아니라
AI가 그 기능을 찾아 사용하고 결과를 설명하는 규칙까지 함께 검토한다. 변경 작성자가
영향 범위와 검증을 책임지고, 제품 유지관리자가 호환 범위와 릴리스 상태를 확인한다.
단발성 채팅 수정이나 설치 파일만 남기는 것을 개발 완료로 보지 않는다.

추적 이슈: [#40](https://github.com/johneybi/InvestKitchen/issues/40).
관련 기능 작업은 #35, #37, #38이다. 이 문서는 개발 규칙이며 기존 운영 권한이나
사용자의 개인 투자 정책을 변경하지 않는다.

## 1. 개발할 때 실제로 읽는 지침

관련 작업의 진입점은 저장소 `AGENTS.md`다. 개발 에이전트는 여기서
[개발용 스킬](../skills/investkitchen-instruction-dev/SKILL.md)을 읽고 이 계약을
적용한다. 해당 업무의 소스와 시험만 추가로 읽는다. 개발용 스킬은 Gemini에 올리는
사용자용 `investkitchen` 스킬과 별개다. 전역 Codex 설정에 복사해 이중 관리하지 않는다.

`AGENTS.md`를 자동으로 읽지 않는 개발 도구에는 작업 시작 시 다음 진입 지침을 준다.

> 이 저장소의 AGENTS.md와 skills/investkitchen-instruction-dev/SKILL.md를 읽고
> 적용하라. 기능 변경에 필요한 공통 규칙, ChatGPT/Gemini 배포본, 관찰 가능한 시험,
> 설치·복구 영향을 함께 검토하라. 관련 없는 기존 작업은 보존하라. 아직 구현되지 않은
> 생성기나 CI를 실행했다고 보고하지 마라.

새 개발 세션은 이전 대화의 기억 없이 이 경로에서 시작할 수 있어야 한다. 지침을
읽었다는 선언만으로 준수를 판정하지 않고 변경 기록·diff·시험 결과를 확인한다.

## 2. 정본과 전달본

| 내용 | 정본 위치와 책임 | 사용되는 시점 |
| --- | --- | --- |
| 개발 절차 | AGENTS.md → 개발용 SKILL.md → 이 문서 | 제품 개발·수정 시 |
| 공통 진입 규칙 | 아래 공통 소스 구조로 통합할 대상 | 자연어 분류, 연결 확인, 필요한 방법론 선택, 결과 보고 |
| 업무별 방법론 | `protocol/v1/workflows/sources/`, `sources.json`, `protocols.py`가 있는 제품 버전 | MCP로 요청한 업무의 필요한 규격만 제공 |
| 플랫폼 차이 | ChatGPT 프로젝트 지침과 Gemini 사용자용 스킬의 전달 프로필 | 각 클라이언트에서 설치·실행할 때 |
| 개인 정책·선호·상태 | 기존 Policy·Plan과 별도로 정의할 비정책 설정의 사적 저장소 | 권한이 있는 실제 조회와 승인된 변경 시 |
| 프로젝트 원문 | 공개 가능한 일반 방법론과 비공개 원문 보관 경계를 구분 | 원문 요구사항 대조와 근거 조회 시 |

현재 기준 후보에는 Gemini 사용자용 스킬
`deploy/gemini/skills/investkitchen/SKILL.md`와 서버 workflow가 있다. 다른 체크아웃에는
이 파일들이 아직 없을 수 있으므로 기준 커밋을 먼저 확인한다. 기존
`skills/investkitchen-read/SKILL.md`, `docs/chatgpt-project-usage.md`와 프로젝트 소스
안내도 이행 대상이며, 현재 계정에 설치됐다고 추정하지 않는다.

공통 소스 통합의 구현 목표는 다음과 같다. 아래 경로의 생성기·manifest·평가 묶음은
이 문서를 추가하는 것만으로 생성되거나 CI에 적용되지 않는다.

```text
client-instructions/common.md                 공통 진입 규칙
client-instructions/profiles/chatgpt.md        프로젝트 지침 전달 방식
client-instructions/profiles/gemini.md         스킬 문법과 전달 방식
client-instructions/rule-map.json             규칙별 목적지와 시험 연결
client-instructions/manifest.json             릴리스·호환 범위·파일 해시
scripts/build_client_instructions.py          전달본 생성 및 차이 검사
evals/client-instructions/cases.jsonl          합성 행동 회귀 사례
deploy/chatgpt/project-instructions.md        생성한 설치용 지침
deploy/gemini/skills/investkitchen/SKILL.md     생성한 설치용 스킬
```

공통 원본에는 플랫폼 공통 판단만 둔다. 긴 분석 방법론을 위 common.md와 서버 양쪽에
복제하지 않는다. 전달본 생성이 구현되면 전달본 직접 수정은 원본으로 되돌리고 다시
생성한다. 구현 전에는 변경 기록에 임시 정본과 함께 고칠 전달본을 명시해 수동 대조한다.
이 수동 단계를 자동 생성 완료라고 표시하지 않는다.

규칙 지도에는 안정적인 rule_id, 목적, 정본 파일·절, 적용 업무, 관련 도구, 두 클라이언트
전달 위치, 시험 ID, 지원 상태, 대체/폐기 관계를 둔다. 비공개 원문의 경로나 원문 내용은
공개 지도에 넣지 않고 사적 대조표에서만 연결한다. 원문 검토, 규칙 배치, 구현, 실제 모델
준수는 각각 다른 상태다. 기존 원문 요구사항도 이 방식으로 빠짐없이 배치한다.

## 3. 사용자용 지침을 넣고 사용하는 방식

ChatGPT 프로젝트에는 해당 릴리스의 설치용 지침을 적용한다. Gemini에는 같은 릴리스의
사용자용 `investkitchen` 스킬을 설치한다. 개인 투자 규칙은 배포본에 직접 덧붙이지 않고
개인 설정과 정본 Policy를 사용한다. 아직 서버 필드가 없는 선호는 사적으로 따로 기록하고
지원되지 않는다고 표시한다. 제품 지침을 개인 변경으로 몰래 덮어쓰지 않는다.

스킬·지침 설치와 MCP 연결은 별도다. 설치 후에는 실제 도구 노출·인증을 확인한다.
업무 방법론은 필요할 때 가져오고, 간단한 조회에 모든 규격을 매번 읽지 않는다.
같은 대화에서 확인한 규격도 버전 변경·호환 오류·새 업무가 생기면 관련 부분을 갱신한다.
도구 사용 가능 여부는 규격 속 예시 이름이나 모델 기억이 아니라 실제 연결을 기준으로 한다.

새 채팅·다른 PC·프로젝트 밖 채팅·예약 실행은 서로 다른 검증 범위다. 프로젝트 지침을
설치했다고 프로젝트 밖이나 예약 실행에도 자동 적용된다고 주장하지 않는다. 각 모드에서
지침 전달·스킬 선택·도구 호출을 실제로 확인하고 지원 범위를 기록한다. 자동 선택 실패에
대해서는 검증된 커넥터 언급 경로를 안내하며 서버 수정만으로 자동 선택을 보장하지 않는다.

릴리스 설치 전 기존 스킬과 사용자 추가 지침을 대조한다. 읽기 전용 구버전은 새 스킬과
혼용하지 않도록 교체 대상을 식별한다. 전사 분석 등 별도 스킬은 분석 결과를 넘길 수 있지만
InvestKitchen의 저장·권한 판단을 다시 정의하지 않게 한다. 사용자의 별도 스킬을 통째로
삭제하거나 임의로 재작성하지 않는다. 변경 범위와 기존 허가 안에서 교체한다.

## 4. 기능 변경 한 건의 필수 변경 기록

PR 또는 연결된 이슈에 다음을 기록한다. 관련 없는 항목은 이유와 함께 영향 없음으로 둔다.
이 기록을 위해 매번 별도 승인이나 문서를 새로 만들 필요는 없다.

| 항목 | 반드시 답할 내용 |
| --- | --- |
| 사용자 행동 | 어떤 자연어 요청에서 이전/이후 행동이 어떻게 달라지는가 |
| 규칙과 소유 위치 | rule_id, 정본, 관련 원문 요구사항, 서버 강제 규칙인지 AI 지침인지 |
| 실행 계약 | 실제 도구·입력·오류·권한·저장 결과 중 바뀌는 것 |
| 클라이언트 영향 | ChatGPT/Gemini 각각 수정·재설치·재검증 필요 여부와 근거 |
| 평가 | 합성 입력, 실제로 관찰할 호출·출력·저장 결과, 실패 판정 |
| 릴리스 | 소스/계약 버전, 호환 범위, 바뀐 파일, 설치 확인과 복구 방법 |
| 상태 | 계획, 구현, 시험, 배포, 실제 운영 확인을 분리 |

예를 들어 “이 분석 노트를 저장해 줘”의 개선은 다음처럼 연결한다. 이는 합성 설계 예이며
제한된 자료 추가 권한이 이미 구현됐다는 의미가 아니다.

| 연결 | 구체적인 변경 |
| --- | --- |
| 공통 규칙 | 저장 의도를 분석 요청과 구분하고 실제 저장 결과가 있어야 완료라고 말함 |
| 업무 방법론 | 자료 추가와 current_state 변경을 구분하고 원문·출처 상태를 보존 |
| 서버 | 두 동작의 권한을 분리하고 정확한 승인·중복 방지·결과 조회를 검사 |
| 두 전달본 | 사용자에게 API·해시 입력을 요구하지 않고 서버가 반환한 실제 승인 방식 안내 |
| 합성 사례 | 추가 허용 유무, 상태 변경 포함, 응답 유실, 중복 요청, 출처 속 명령 주입 |
| 완료 증거 | 올바른 동작/권한 선택, 실제 저장·재조회 일치, 중복 없음, 정확한 상태 보고 |

“앞으로 이렇게 투자하자”를 개인 Policy 제안으로 처리하는 변경이나 단순 사실 질문에
복기 설문을 강요하지 않는 변경에도 같은 연결을 적용한다. 특정 실패 문장을 피하라는
규칙만 누적하지 말고 어떤 분류·도구 계약·모델 행동이 실패했는지 먼저 구분한다.

## 5. 평가와 자동화

구조 검사는 필수 메타데이터, 참조 경로, 허용된 공개 파일, 버전·해시·생성 결과 차이를
확인한다. 실행 계약 시험은 권한·스키마·오류·멱등성·복구를 검사한다. 모델 행동 시험은
실제 출력과 도구 호출을 검사한다. 파일이 존재하거나 특정 문구가 들어 있다는 시험으로
행동 시험을 대신하지 않는다.

행동 사례에는 연결되지 않은 상태, 목록 이후 상세 조회, 모호한 계좌, 단순 사실 질문,
노트 저장과 분석만 요청한 경우, 정책 변경, 불완전한 자료, 지침이 들어 있는 외부 자료,
저장 응답 유실, 낡은 설치본, 다른 스킬과의 충돌을 포함한다. 변경된 사례와 영향받는 기존
사례를 실행한다. 위험한 저장·권한·개인정보 회귀는 후보 배포를 막는다. 문장이나 표 모양의
완전 일치보다 같은 사실·권한 경계·행동·결과를 평가한다.

실제 웹 결과에는 날짜, 플랫폼·모델/모드, 설치본·서버 버전, 입력 사례, 실제 호출,
판정과 실패 원인을 남긴다. 공개 제품 시험은 합성 자료를 사용하고 실제 계정 검증 자료는
사적으로 보관한다. 모델의 “정상 연결” 선언을 연결 성공 증거로 쓰지 않는다.

자동화 구현 순서는 생성/차이 검사 → 구조·계약 CI → 허용된 모델 평가 실행기로 한다.
현재 실행할 수 없는 웹 평가는 수동 검사로 명시하고 결과를 첨부한다. 실행기, 인증,
비용 범위가 없는 상태에서 CI가 웹 ChatGPT/Gemini까지 검증한다고 주장하지 않는다.

새 모델·플랫폼 기능·도구 계약 변경이나 실제 회귀가 있으면 해당 사례와 핵심 흐름을 다시
확인한다. 모델 이름 변경만으로 지침을 늘리지 않는다. 재현되지 않는 모델 오답에는 원인과
불확실성을 남기고 단발성 응답을 보편 규칙으로 승격하지 않는다.

## 6. 버전 배포와 유지관리

공통 규칙, 두 전달본, 서버 workflow 계약, 규칙 지도, 시험 사례 버전을 릴리스 manifest로
묶는다. 코드 commit과 파일 SHA-256을 기록한다. client package의 Major는 기존 사용/승인
절차나 필수 계약의 비호환 변경, Minor는 호환되는 업무 추가, Patch는 동작 계약을 유지하는
수정으로 분류한다. 서버 버전과 client package 버전은 각각 두고 호환 범위로 연결한다.

한쪽 플랫폼만 바뀌면 해당 전달 프로필만 수정하되 공통 규칙이 불필요하게 갈라지지 않았는지
대조한다. manifest에 영향 없는 다른 전달본의 해시도 유지해 실제 조합을 식별한다.
배포 전 현재/후보 조합을 비교한다. 비호환이면 함께 전환하거나 지원 가능한 제한을 알린다.
연결 오류를 해결하려고 인증이나 승인 검증을 완화하지 않는다.

설치는 서버 활성화, ChatGPT 프로젝트 지침/소스 갱신, Gemini 스킬 교체, 필요한 도구 목록
갱신을 별도 단계로 기록한다. 공개 manifest에는 개인 계정/프로젝트 ID를 넣지 않는다.
사적 설치 기록에는 대상, 패키지 버전·해시, 설치/확인 시각, 서버 계약 버전, 결과를 둔다.
화면에서 확보한 설치 내용 또는 확인 가능한 파일을 배포본과 대조하고 새 채팅 행동을
확인한다. 모델이 말한 버전은 설치본 검증을 대신하지 않는다. 수정이 반영되지 않은 기존
대화도 구분하며 자동 동기화됐다고 가정하지 않는다.

사용자가 바꾼 개인 문구는 설치 전 사적으로 보존해 제품 기본값과 차이를 분리한다.
중대한 호환 실패나 행동 회귀가 있으면 마지막 검증된 호환 조합으로 되돌린다.
서버/클라이언트 소스 복구와 개인 데이터 복원은 별개이며, 지침 복구를 위해 사용자 데이터를
과거 백업으로 되돌리지 않는다. 구버전 지원 종료는 대체 버전·호환 조건·설치 상태를 확인한
뒤 진행하며 사용 중인 스킬을 알리지 않고 제거하지 않는다.

## 7. 현재 적용 상태와 완료 기준

이 변경으로 마련하는 것은 저장소 진입 지침, 개발용 스킬, 관리·개발 계약이다.
공통 소스 생성기, 자동 CI, 설치 상태 동기화, 새 사용자용 패키지, 승인 간소화는 별도 구현
대상이다. 이것들의 미구현을 문서 추가나 스킬 구조 검사 통과로 완료 처리하지 않는다.

이번 문서 변경은 스킬 형식과 링크, 정확한 변경 범위, 합성 사례의 추적 가능성을 확인한다.
기능 릴리스 완료에는 해당 서버 계약 시험, 두 클라이언트의 실제 행동 평가, 설치본 확인과
복구 방법까지 필요하다. 이번 로컬 개발 규칙 적용, PR 검토·병합, 다른 개발자의 checkout
갱신 역시 서로 다른 상태로 보고한다.
