### 1. Windows가 확정하는 발행물

필수 필드·열거값·배열 범위는 Windows와 NAS가 공유할 [요청 JSON Schema](../protocol/v1/schemas/market-edition-ingest.schema.json)에 정의한다. 양쪽 모두 Draft 2020-12의 날짜·시각·UUID·URI 형식 검사를 활성화한다. 수신기는 별도로 참조 무결성·기준 시각·바이트 한도를 검사한다. 출처 ID와 후보 ID는 각 배열 안에서 유일해야 한다. 누락 출처, 내부 주소·파일 경로가 포함된 원문 참조는 거절한다. 본문은 인증된 뷰어를 추가할 때도 신뢰하지 않는 Markdown으로 취급한다.

사람용 장전판의 보관이 성공하면 발행 기록으로 판 종류를 확인하고 전송용 UUID와 요청 바이트를 고정한다. 보관판과 전송판 사이의 대응 관계를 발송 장부에 남긴다. 같은 보관판 ID에서 원본이 바뀌면 전송을 보류한다. 거래용 봉인판과 장중판은 장전판 발송 대상에서 제외한다.

편집 원문의 후보 순서를 보존하고, 선정 이유와 재확인 조건은 같은 판에서 근거를 찾을 수 있는 문장으로 작성한다. 연결을 확인한 출처만 `evidence[].source_ids`에 넣고, 근거 부족은 `evidence_gap`에 기록한다. 조사가 일부만 완료됐으면 `coverage=partial`과 `gaps`로 범위를 표시한다. 확인된 전체 조사 모집단이 없으면 `screened_count`를 null로 둔다.

발송 단위는 UTF-8 JSON 한 건이다. 아래는 한 종목만 있는 합성 초판의 **전체 요청 본문**이다. 공개 자료의 짧은 발췌와 출처를 담고, 실제 방송 원본·개인 보유·계좌·로컬 파일 경로·인증 정보는 전송 대상에서 뺀다. 원래 보고서가 이 경계를 넘는 경우 내보내기를 보류하고 수정본을 새로 검토한다.

원본 판을 확정할 때 발송 패키지 또는 ‘내보내기 대기’ 표지도 함께 남긴다. Windows 작업이 재시작하면 사람용 장전 발행 기록·보관 manifest·접수 장부를 대조해 보관 직후 중단된 전송도 복원한다. 내용이 바뀐 파일을 기존 ID로 재생성하지 않도록 최초 전송 바이트를 접수까지 보존한다.

```json
{
  "schema_version": 1,
  "edition_id": "10000000-0000-4000-8000-000000000001",
  "market": "KR", "trade_date": "2026-11-20", "kind": "preopen",
  "parent_edition_id": null,
  "source_cutoff_at": "2026-11-20T07:00:00+09:00",
  "published_at": "2026-11-20T07:04:00+09:00",
  "snapshot": {
    "snapshot_id": "20000000-0000-4000-8000-000000000001",
    "scope": "합성 거래소 공시 표본", "screened_count": 12,
    "coverage": "partial", "gaps": ["거래대금 자료 미도착"],
    "sources": [
      {"source_id":"s1","publisher":"합성 공시처","title":"공급계약 정정",
       "url":"https://example.org/disclosures/fixture-1",
       "known_at":"2026-11-20T06:52:00+09:00","excerpt":"계약 기간을 연장했다."}
    ]
  },
  "report": {
    "title": "장전 시장판", "summary": "계약 정정 1건을 우선 확인한다.",
    "themes": ["공급계약"], "body_markdown": "## 공급계약\n합성종목 A의 계약 기간이 연장됐다.",
    "candidates": [
      {"candidate_id":"KRX:000001","name":"합성종목 A","status":"watch",
       "reason":"계약 기간 정정","recheck":"금액 변경 공시 여부",
       "evidence":[{"type":"fact","text":"정정 공시에서 계약 기간 연장을 확인했다.","source_ids":["s1"]}]}
    ]
  }
}
```

| 필드 | 수신 규칙 |
|---|---|
| 식별·시각 | 판·조사 ID는 발행기가 한 번 부여하는 UUID다. 같은 발행 재시도에는 같은 ID와 같은 바이트를 쓴다. 첫 버전은 `KR/preopen`, 거래일은 서울 현지의 유효한 ISO 날짜다. 시각은 오프셋 있는 RFC 3339로 받고 UTC로 비교한다. 출처의 최초 확인 시각 ≤ 자료 마감 ≤ Windows 발행 시각이어야 한다. NAS는 별도 `accepted_at`을 기록한다. 휴장·미래 예약판을 자동으로 오늘 판으로 돌려 쓰지 않는다. |
| 조사 스냅샷 | 조사 범위·마감 시각, `coverage=complete/partial`, 공백, 조회 당시 확보한 출처를 고정한다. `screened_count`는 조사한 모집단 수이며 모르면 null이다. 후보 수는 `report.candidates` 길이로 계산한다. 같은 조사 ID를 재사용할 때 최초 저장한 정규화 내용·마감 시각과 일치해야 한다. 수신기가 키 순서를 무시한 파싱 결과를 비교하며, 배열 순서는 내용에 포함한다. |
| 편집·후보 | 배열 순서가 Windows 편집 순서다. `candidate_id`는 해당 판에서 유일한 거래소·종목 식별자다. 국내 종목은 기존 식별 규칙에 맞는 6자리 코드를 문자열로 보존한다. `status=priority/watch/excluded` 각각의 선정·제외 이유와 재확인 조건을 담는다. 신규 후보가 없는 판도 유효하다. 누락과 ‘검토 후 제외’를 구별한다. |
| 종목 근거 | `type=fact/interpretation`, 편집 문장, 같은 스냅샷 안의 출처 ID를 연결한다. 출처마다 공개 HTTPS 참조 또는 공개 문서 식별자(`document_ref`), 발행처·제목·당시 확보한 짧은 발췌·확인 시각을 담는다. URL과 문서 참조 중 적어도 하나가 필요하다. 제출한 근거마다 유효한 출처가 하나 이상 있어야 한다. 출처 자체가 없는 후보는 빈 근거 배열과 필수 `evidence_gap` 사유로 보존한다. NAS는 원격 URL을 가져오지 않는다. 웹도 자료 속 문장을 도구 실행 지시로 사용하지 않는다. |
| 크기 | 초깃값은 비압축 요청 2 MiB, 후보 1,000개, 출처 2,000개, 후보당 근거 32개, 근거당 출처 4개다. 제목·이름 160자, 요약 1,000자, 개별 편집 문장·출처 발췌 600자, URL 2,048자, 본문은 디코딩한 문자열의 UTF-8 256 KiB, 테마·공백 각각 32개 × 160자로 제한한다. 필드 초과·알 수 없는 필드·중복 JSON 키·잘못된 참조를 거절하고 조용히 잘라 저장하지 않는다. 스키마의 `maxLength`는 문자 수이므로 수신기가 별도로 `len(body_markdown.encode("utf-8")) <= 262144`를 검사한다. 초과하면 413으로 거절한다. 한글 ‘가’ 90,000자는 270,000바이트로 실패해야 한다. 실제 발행판 분포로 상한을 검증한다. MCP HTTP 요청 크기 제한과는 독립이다. |

### 2. 수신 방법·권한·접수증

[전용 Synology Compose 프로필](../deploy/synology/market-edition.md)의 수신기는 LAN 주소에 HTTPS를 바인딩한다. 양쪽이 상대 인증서를 검증한다. 발행 범위는 운영자가 별도 서명한 승인으로 바인딩하며, 승인 확인에 실패하면 저장을 거절한다. 기존 MCP와 공개 뷰어에는 이 쓰기 경로를 연결하지 않는다.

- **요청** — `PUT /internal/v1/market-editions/{edition_id}`, `Content-Type: application/json`, `X-Payload-SHA256`은 전송하는 정확한 UTF-8 본문의 소문자 SHA-256(64자리)이다. 발행기는 파일 완성 후 같은 바이트를 재사용한다. NAS는 크기를 제한해 읽은 뒤 직접 해시를 계산한다. 경로와 본문의 판 ID가 일치해야 한다.
- **쓰기 허가** — NAS가 TLS 클라이언트 인증서로 확인한 신원으로 발행자를 결정한다. NAS 운영자가 신뢰한 승인 경로에서 미리 승인한 자동 발행 정책에 인스턴스·발행자·발행 자격증명 바인딩·허용 시장/판 종류·`market_edition.publish`·유효기간을 묶는다. 수신기는 서버가 검증할 수 있는 승인 기록과 현재 grant를 매 요청 및 커밋 직전에 확인한다. Windows 본문의 ‘승인됨’ 표시나 해시는 승인 근거가 될 수 없다. 재사용할 경로에도 이 제한된 사전 승인 검증이 있어야 한다. 승인 미구성·만료·철회 시 로컬 대기열에 남긴다. 기존 계좌별 승인과 Session Authority 권한을 전용하지 않는다. [기존 신뢰 승인 경계](../protocol/v1/security/trusted_approval.py)
- **저장 순서** — 발행기별 업로드 대기열을 안정 저장하고 같은 거래일·시장·판 종류 안에서는 순서대로 전달한다. 초판의 `parent_edition_id`는 null이다. 수정판은 직전 판 ID를 넣고, 자료 마감 시각은 직전보다 이를 수 없다. 같은 자료를 편집만 정정하면 같은 마감 시각과 조사 ID를 쓸 수 있다. NAS가 처음 수락한 판에 1을, 후속 판에 직전 번호 + 1을 부여한다. Windows 파일명의 번호는 NAS 판 번호로 신뢰하지 않는다.
- **응답** — 최초 커밋은 HTTP 201, 동일 요청 재전송은 200과 원래 접수증이다. 접수증에는 `edition_id, revision, parent_edition_id, market, trade_date, kind, publisher_id, snapshot_id, payload_sha256, accepted_at`을 반환한다. Windows는 ID·해시·날짜·종류를 대조하고 로컬에 접수증을 기록한 다음에만 발송 완료로 전환한다. 연결이 끊기거나 응답을 잃어도 같은 요청을 재전송하면 된다.
- **실패** — 깨진 JSON·경로 ID·해시는 400, 인증/권한 실패는 TLS 거절 또는 401/403, 초과 크기는 413, 스키마·시각·출처 오류는 422다. 409는 `edition_id_conflict`(같은 ID 다른 바이트), `snapshot_conflict`, `head_conflict`로 구분한다. 마지막 경우 현재 권한 범위의 최신 판 ID를 알려주되 자동으로 부모를 바꿔 재제출하지 않는다. 순서 역전이면 선행 판부터 복구하고, 실제 편집 충돌이면 최신판에서 변경을 검토한 뒤 새 ID로 발행한다. 네트워크 장애·503만 지수 백오프로 재시도하고 재기동 후 대기열을 재개한다.

**합성 접수증.** 위 요청 코드 블록의 첫 `{`부터 마지막 `}`까지 LF 줄바꿈, 마지막 개행 없이 계산한 해시다. 실전에서는 매번 실제 전송 바이트를 계산한다.

```json
{
  "edition_id": "10000000-0000-4000-8000-000000000001",
  "revision": 1,
  "parent_edition_id": null,
  "market": "KR",
  "trade_date": "2026-11-20",
  "kind": "preopen",
  "publisher_id": "windows-analyst-fixture",
  "snapshot_id": "20000000-0000-4000-8000-000000000001",
  "payload_sha256": "94d0d4abef5ae569b12c0d12662a44fa8fb7f22c816c294050fddcf48a057a54",
  "accepted_at": "2026-11-20T07:04:08+09:00"
}
```

### 3. NAS 저장과 원자성

자동 발행 권한은 전송 자격증명과 독립적으로 관리자가 승인하며, 서버는 정책 ID·버전·범위·유효기간·철회를 검증한다. 기존 서버 측 신뢰 승인 기록이 이 요건을 충족하면 재사용한다. 내부 HTTPS 수신기를 신설하고 적합한 승인 경로가 없다면 운영자 신뢰 키로 서명한 로컬 정책을 검증한다. 발행 자격증명으로 승인 정책을 발급·변경할 수 없다.

수신기는 NAS 로컬 파일시스템의 전용 SQLite DB에 쓰고 MCP는 같은 DB를 읽기 전용(`mode=ro`)으로 연다. 수신기만 쓰기 권한을 가지는 별도 데이터 볼륨과 자격증명을 쓴다. 제품 Git, 개인 계좌 이력, Session Exchange, 비밀, 백업은 기존 경계를 유지한다. 첫 구현은 rollback journal·`synchronous=FULL`을 쓰고 읽기 측에는 변경 중인 DB를 `immutable`로 열지 않는다. 쓰기 중 비정상 종료로 복구가 필요한 저널(hot journal)이 남으면 RO 조회는 `unavailable`로 응답한다. 수신기는 쓰기 가능한 연결로 복구·일관성 확인을 마친 뒤 준비 완료를 표시한다. 부분 쓰기 중 강제 종료, RO 조회, 수신기 재기동, 마지막 정상판 재조회와 중단된 요청 재전송을 차례로 시험한다. [SQLite 트랜잭션](https://www.sqlite.org/lang_transaction.html) · [SQLite 읽기 전용 URI](https://www.sqlite.org/uri.html)

| 논리 테이블 | 키와 용도 |
|---|---|
| snapshots | `(scope_id, snapshot_id)` 기본 키. 마감 시각과 검증한 스냅샷 JSON을 저장한다. |
| editions | `(scope_id, edition_id)` 기본 키, `UNIQUE(scope_id, market, trade_date, kind, revision)`. 부모·작성자·원문 해시·접수 시각·검증한 요청 원본 바이트·스냅샷 참조·제목·요약·테마·본문을 저장한다. 같은 행에서 접수증을 재구성한다. |
| candidates | `(scope_id, edition_id, candidate_id)` 기본 키, 판 내 표시 순번 유일. 이름·편집 상태·사유·재확인 조건·근거 배열을 저장한다. 모든 참조는 같은 범위의 불변 판 또는 스냅샷으로만 연결한다. |

`scope_id`는 서버의 읽기·쓰기 grant에서 결정한다. 한 트랜잭션에서 ① `BEGIN IMMEDIATE` ② 동일 범위·판 ID·발행자·해시 확인(다른 발행자는 거절하고 일치하면 **현재 최신판 검사보다 먼저** 원접수증 반환) ③ 해당 스트림 최종 번호의 판과 부모 비교 ④ 스냅샷·판·후보 행 삽입 ⑤ 커밋 순으로 처리한다. 최신판은 커밋된 행 중 해당 스트림의 최대 번호로 구한다. 두 수정판이 동시에 같은 부모를 제시해도 하나만 성공한다. 최신 파일 링크나 별도의 가변 인덱스를 만들 필요가 없다. 중간 예외는 전체 롤백한다. 디스크 부족·잠금 시간 초과·복구 중인 DB는 일시 불가로 보고하며 ‘미도착’으로 표시하지 않는다. 백업은 SQLite 일관 백업으로 만들고 복원 후 판·후보·접수증이 일치하는지 확인한다. Discord 발송은 별도 작업이며 전송 실패로 커밋한 판이 취소되지 않는다.

### 4. 웹 GPT의 두 조회 도구

**Mac 로컬 검증.** 읽기 모듈은 신뢰된 호출자가 지정한 자료 범위에서 SQLite `editions`의 커밋된 요청 바이트(`payload` 열)를 읽는다. 한 번의 조회에서 요약·후보·출처를 같은 판으로 구성한다. 날짜로 연 직후 수정판이 들어오는 경우, 이전 판의 다음 페이지, 부분 조사와 근거 공백, 범위 밖 조회를 합성 DB로 시험한다. 재실행은 `python -m pytest -q protocol/v1/tests/test_market_edition_reader.py`다. NAS 수신기·MCP 권한 연결·실제 웹 조회는 별도 인수 항목이다. [읽기 모듈](../protocol/v1/runtime/market_edition_reader.py) · [합성 인수 시험](../protocol/v1/tests/test_market_edition_reader.py)

두 도구는 같은 저장소를 사용한다. 이름·필드·한도는 **제안 계약**이다. 웹은 읽기 전용으로 명시적으로 허가된 범위에서만 호출한다. 각 페이지는 JSON UTF-8 32 KiB 이내로 직렬화하고 한도를 넘기기 전에 완전한 행 단위로 페이지를 닫는다. 날짜로 열었던 목록도 다음 페이지부터는 반드시 판 ID를 쓴다.

| 도구 | 입력 | 반환 |
|---|---|---|
| `get_market_edition` | 첫 조회는 `market, trade_date, kind`. 고정 판 재조회는 `edition_id`. 두 선택자는 배타적이다. 선택적 `limit`은 1~30(기본 15), `offset`은 0부터 시작하며 0보다 크면 판 ID가 필수다. | 판·부모·번호·조사 ID·발행자·거래일·자료 마감·발행·접수 시각, 인증된 본문 고정 링크 `edition_url`, 제목·요약·테마·조사 범위·공백, `screened_count, candidate_count`, 후보별 `candidate_id,name,status,reason,recheck`, `next_offset`. 편집 순번대로 제공한다. |
| `get_market_candidate_evidence` | `edition_id, candidate_id` 필수. 선택적 `offset, limit`(기본 3, 최대 8). 날짜 단독이나 ‘최신’ 선택자는 허용하지 않는다. | 같은 판·조사 ID·번호·자료 마감, 후보 이름·편집 상태·선정/제외 이유·재확인 조건, 순서대로 해당 근거 문장·종류와 참조한 출처의 제목·발행처·원문 참조·당시 발췌·확인 시각, `evidence_total, evidence_gap, next_offset`. |

`next_offset`은 실제 돌려준 마지막 행 다음 위치이며 끝이면 null이다. 페이지 경계에서 한 행도 못 담는 입력이 생기지 않도록 NAS가 저장 전 **목록 헤더+한 후보** 및 **상세 헤더+근거 한 건과 그 출처**가 각각 32 KiB 안에 드는지 확인한다. 서버에서 전송 중 필드를 잘라내지 않는다. 다음 호출마다 grant·판 소속·후보 소속을 검증한다. 후보가 다른 판에만 존재할 때 최신판이나 심벌 검색으로 자동 대체하지 않는다. `edition_url`은 신뢰된 NAS 뷰어 설정과 불변 판 ID로 만든 주소다. 사용자는 이 링크에서 전문을 읽고 웹은 목록의 재확인 조건까지 한 번에 표시한다. 상세 도구는 출처·당시 발췌가 필요할 때 호출한다.

**합성 대화에서의 호출 순서**

1. “오늘 장전 재료 보여줘.” → `get_market_edition({"market":"KR","trade_date":"2026-11-20","kind":"preopen"})`. ‘오늘’은 한국 시장의 요청 날짜로 해석한다. 위 입력의 접수 후라면 v1, ID `10000000-0000-4000-8000-000000000001`, 마감 07:00 KST, 12개 조사·편집 1개, 거래대금 공백을 보여준다.
2. “그 종목을 왜 넣었어?” → `get_market_candidate_evidence({"edition_id":"10000000-0000-4000-8000-000000000001","candidate_id":"KRX:000001"})`. 그사이 v2가 발행돼도 v1의 계약 기간 정정·출처 s1·06:52 확인 시각과 재확인 조건을 돌려준다. 사용자가 최신판을 요청하면 1단계부터 새 판으로 연다.
3. 날짜 조회에 그날 판이 없으면 `status=not_published`와 요청한 시장·날짜·종류를 반환한다. 전 거래일 판을 대신 보내지 않는다. 승인 범위 내 고정 판·후보 미발견은 `not_found`, 허가 없는 도구 호출은 거절, 저장 장애는 `unavailable`이다. 권한 밖 ID의 존재를 노출하지 않는다. 일부 출처 누락은 `ok`와 공백 필드로 구분한다. 새 대화에서는 날짜로 그날 최신판을 열거나, 이미 알고 있는 판 ID로 재개한다. 개인 장전 분석은 별도의 기존 계좌·계획 읽기를 사용한다.

**동일 합성판에서 돌려주는 두 응답.** 첫 번째의 `candidates[].status`와 두 번째의 `candidate_status`는 같은 편집 상태다. 최상위 `status`는 도구의 조회 결과다.

### 5. 구현 위치·인계·완료 기준

| 순서 | 바꿀 곳 | 확인할 결과 |
|---|---|---|
| 1. 발행기 매핑 | 실사에서 확인한 사람용 장전 보관 성공 지점에 로컬 내보내기를 연결한다. 표본 판에서 모든 편집 후보의 필수값과 출처 연결을 대조한다. | 같은 판을 두 번 처리해 전송 UUID·요청 바이트가 같은지 확인한다. R22·장중판 제외, 초판·부분 자료·후보 0개·수정판·누락 참조는 합성 입력으로 검증한다. |
| 2. NAS 저장·수신 | `protocol/v1/runtime/`에 전용 저장·조회 모듈, `protocol/v1/transport/`에 내부 수신 명령을 둔다. 배포에는 수신기 전용 인증·승인 검증, 쓰기 볼륨과 읽기 측 RO 마운트를 추가한다. | 권한 만료·다른 발행자·해시 불일치·부분 전송·커밋 직전 종료·접수증 응답 유실·같은 부모 동시 발행·디스크 부족을 재생한다. 실패한 판의 요약이나 일부 후보가 조회되면 미통과다. |
| 3. MCP 읽기 | 공통 gateway와 로컬 라우터, 도구 카탈로그, ChatGPT stdio의 목록·호출 정책, 런처의 저장소 배선에 두 도구를 추가한다. 신규 `market_edition.read`를 서버가 인증한 인스턴스·자료 범위에 묶고 미설정 시 두 도구를 숨기며 직접 호출도 거절한다. 일반 시세 권한을 가진 클라이언트에 자동 개방하지 않는다. Gemini HTTP는 읽기 grant와 가시성 목록에 명시한 경우에만 같은 계약을 적용한다. [공통 라우터](../protocol/v1/transport/stdio_rpc.py) · [카탈로그](../protocol/v1/transport/tool_catalog.json) · [ChatGPT stdio](../protocol/v1/transport/mcp_stdio.py) · [Gemini 읽기 경계](../protocol/v1/transport/mcp_read_surface.py) | 목록/호출 양쪽에서 무권한 거절, 다른 범위 ID 비노출, 다중 페이지 순서 보존, 전 거래일 대체 금지, v1 요약 직후 v2 접수 후에도 v1 상세·다음 페이지가 유지된다. |
| 4. 웹 인수 | 공통 브리핑 지침과 클라이언트별 전달 설정에 ‘날짜로 한 번 → 같은 ID로 상세’ 규칙을 연결한다. 실제 NAS 접수와 ChatGPT 새 대화에서 검증한다. 예약 읽기는 별도 실행으로 판정한다. | 거래 보호 의무가 없는 시간 또는 모의 환경에서 Windows 접수 완료 후 PC를 끈다. 이후 웹이 같은 판의 요약·종목 근거·자료 시각을 정확히 표시한다. Discord 한 줄의 고정 링크가 해당 판의 인증된 전문을 여는지도 확인한다. 합성 시험, 배포 버전, 웹에서 확인한 판 ID와 결과를 별도로 기록한다. |

**인증 배선 시 주의할 부분.** 현 stdio 진입점은 서버의 선택적 가시성·호출 인가 훅을 기본 생성자에서 주입하지 않는다. 이 두 도구는 전용 읽기 grant를 로드한 런처에서만 노출하고 목록과 직접 호출에 같은 검사기를 연결한다. grant에서 선택한 단일 연구자료 범위를 저장소 조회까지 전달한다. 요청 메타·모델이 넣은 인자·기존 쓰기 grant로 범위를 결정하지 않는다. HTTP 쪽은 `ReadPermission` 허용값과 범위 모델도 함께 확장한다. 지원 범위가 없는 기존 grant는 기존 도구만 사용할 수 있다. [HTTP grant 모델](../protocol/v1/security/oauth_resource.py)

**후속 웹 편집을 열기 전 확인할 계약.** 첫 출시는 단일 Windows 발행자다. 웹도 정식 수정판을 낼 단계에는 Windows가 같은 스트림의 최신 판 ID와 변경 내용을 인증된 읽기 경로로 확인할 수 있어야 한다. 예를 들어 내부 HTTPS의 head 조회와 고정 판 조회를 함께 정의한다. 409 응답에 실린 ID만 보고 부모를 교체하지 않고 변경분을 재검토한다. 이 절차를 시험하기 전에는 웹의 수정 요청을 초안으로 둔다.

첫 출시의 돌이키기 쉬운 지점은 **Windows의 기존 발행·보관 뒤에 발송을 붙이는 것**이다. 수신이나 읽기에 문제가 있으면 두 도구의 노출과 전송을 중지하고 로컬 발행을 계속한다. 마지막 정상 접수증부터 같은 패키지를 다시 보내 복구한다. 기존 판과 접수증은 보존한다.
