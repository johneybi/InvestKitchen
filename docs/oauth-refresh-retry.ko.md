# 기존 Gemini 연결의 토큰 갱신 재시도

추적 이슈: #52. 상태: 구현·합성 시험·운영 배포 완료. 실제 갱신 이후 성공과 실패가
함께 관측되어 지속 연결의 운영 수락은 미완료다. 아래 운영 검증 기록을 함께 읽는다.

## 원인과 책임

회전식 갱신 토큰을 사용하는 인증 서버에서는 성공한 응답을 클라이언트가 받지 못하고
같은 토큰을 다시 제출하면 해당 승인이 폐기될 수 있다. 운영 메타데이터에서 새 토큰
발급 뒤 이전 토큰과 같은 승인의 접근 토큰이 폐기된 상태를 확인했다. NAS 전체 I/O
지연도 같은 구간에 관측됐으나, Google 내부 재시도 경로를 직접 관측한 것은 아니다.

이 변경의 소유 위치는 `deploy/gemini/oauth_refresh_proxy.py`이다. 자연어 분류나 AI
지침으로 인증 실패를 우회하지 않는다. 기존 issuer와 token URL, MCP URL, 앱 등록을
유지하고 token URL의 내부 중계만 추가한다. 인증 코드는 원래 issuer에 전달한다.

## 실행 계약과 보안 경계

- 지정된 confidential client의 `client_secret_post` 갱신만 대상으로 한다.
- 클라이언트 자격증명, 이전 갱신 토큰, scope, resource를 포함한 **전체 요청**이 같은
  경우만 동시 요청을 합치고, 완료 후 최대 60초 동안 응답을 재사용한다. 조회로 기간이
  연장되지 않는다. 요청 키는 프로세스 임의 키의 HMAC이며 원문을 디스크에 저장하지 않는다.
- 성공 응답을 돌려주기 전마다 원래 클라이언트 자격증명으로 issuer에 introspection을
  수행한다. 활성 상태·클라이언트·만료를 확인하지 못하면 토큰을 반환하지 않는다.
  `expires_in`은 실제 남은 시간으로 줄인다. 권한이나 토큰 수명을 늘리지 않는다.
- 이 60초 안에서는 동일 요청의 재전달을 새 refresh 사용으로 issuer에 보내지 않는다.
  따라서 **해당 짧은 구간의 동일 요청 재사용 감지는 중복 응답으로 대체된다.** 회전을
  끄는 설정과는 다르지만, 배포 검토에서 이 변경을 명시해야 한다. 다른 요청 및 기간이
  지난 요청에는 기존 issuer 검증이 적용된다. 폐기·비활성 응답은 캐시에서도 거부한다.
- 응답은 메모리에만 최대 32개, 각각 64 KiB 이하로 보관한다. 동시 HTTP 처리 수는 8개다.
  포화·불확실한 상류 응답·introspection 장애는 fail closed 한다. 서비스 재시작 시
  기억은 사라진다. 프로세스 장애와 이미 발생한 승인 폐기를 복구하는 기능은 아니다.
- 현재 grant 만료, NAS 승인 범위, 개인 데이터, ChatGPT 전송 경로는 변경하지 않는다.
  신규 네트워크 listener는 loopback 전용이며 `/healthz`는 공개 route에 추가하지 않는다.

## 유지관리와 검증

서버 입력/저장 계약과 자연어 업무 규칙은 바뀌지 않으므로 공통 지침, ChatGPT 프로젝트,
Gemini 스킬은 재설치하지 않는다. 현재 설치본 2026-11-17.2와 조합해 검증한다.

`protocol/v1/tests/test_oauth_refresh_proxy.py`는 중복·동시 요청, 자격증명/scope/resource
변경, 기간 경계, 만료·폐기·조회 장애, 용량, 재시작 및 실제 loopback HTTP 경계를 확인한다.
`deploy/gemini/verify_refresh_proxy.py --authelia <binary>`는 실제 Authelia와 임시 합성
계정으로 코드 발급→첫 갱신→중복 갱신→후속 회전→issuer 재사용 폐기→캐시 거부를 확인한다.
운영 계정·기존 설정을 읽거나 기존 인증 DB를 사용하지 않는다.

로컬 health의 `recent_stages`는 최근 16개의 issuer 교환, introspection, 응답 쓰기
단계에 대해 고정 분류·숫자 상태·소요 시간·시각만 메모리에 남긴다. 토큰, 요청 필드,
오류 원문은 수집하지 않는다. 상태 0은 해당 단계의 예외 또는 쓰기 실패다. 소켓 쓰기
성공만으로 Google이 응답을 수신하거나 새 refresh token을 저장했다고 판단하지 않는다.
health 조회 자체는 기록을 밀어내지 않는다. 이 진단 추가는 인증 판정과 60초 경계를
바꾸지 않으며, 기존 서비스에 자동으로 반영되지 않는다.

운영 재검증에서는 첫 갱신 성공 이후 후속 갱신의 승인 폐기가 재현됐다. 따라서 현재
60초 처리를 연결 유지 문제의 완료된 해결책으로 보지 않는다. 기존 카운터만으로는
응답 유실·지연과 클라이언트의 새 토큰 보관 실패를 구분할 수 없다. 허용 시간을
임의로 늘리거나 회전 검증을 끄기 전에 단계별 증거를 확인해야 한다.

배포는 고정 소스와 현재 edge 설정 해시를 확인하고, 기존 파일의 보호된 복구본을 만든
뒤 별도 loopback service와 정확한 token route만 활성화한다. 실패하면 이전 edge 설정을
복구하고 새 service를 중지한다. 복구 과정에서 OAuth DB나 정본 지식을 되돌리지 않는다.

운영 완료 기준은 기존 Gemini 앱에서 접근 토큰 갱신을 실제 확인한 뒤 계좌/지식 조회,
자연어 지식 추가, 원문 재조회가 재연결 없이 이어지는 것이다. 최소 두 갱신 구간에서
실행 결과와 issuer 상태를 대조한다. 부분 계좌 결과를 완전한 최신 계좌 검증으로 보고하지
않는다. 단위 시험과 합성 issuer 시험은 이 웹 완료 기준을 대신하지 않는다.

## 인증 저장 지연 후보 — 실제 클라이언트 검증 전

운영 진단에서 issuer의 성공 응답에 약 7초가 걸리고, 앞단 연결이 닫혀 응답 쓰기가
실패한 경우를 확인했다. 이는 토큰이 발급됐다는 사실만으로 연결 성공을 판정할 수
없음을 보여 준다. 단일 I/O 표본의 쓰기량만으로 다른 서비스가 원인이라고 판단하지 않는다.

`sqlite_journal.py`는 모든 인증 DB writer를 정지한 상태에서 무결성과 논리 데이터
동일성을 확인하고, SQLite backup API로 보호된 복구본을 만든 뒤 저널만 전환한다.
일상 rollback은 **현재 DB**를 DELETE 모드로 되돌린다. 이전 백업을 덮어써서 새 토큰
취소나 동의를 되돌리지 않는다. WAL 운영 중 백업은 DB 파일만 복사하지 말고 SQLite
backup API를 쓰거나 issuer를 정지하고 checkpoint한 뒤 수행해야 한다.

이 후보는 Authelia **4.39.28** 및 go-sqlite3 **1.14.52**에 한정해 검증한다. 드라이버의
기본 synchronous는 NORMAL이므로 WAL만 켜면 안 된다. `full_wal_storage_path`는
`_journal_mode=WAL`, `_synchronous=FULL`, `_txlock=immediate`를 모두 명시한다.
issuer가 뒤에 추가하는 DSN 문자열을 마지막 무시되는 파라미터 값으로 받는 버전 의존
어댑터다. 일반 path 설정은 보존하고 해당 service의 환경 override로만 사용한다.
issuer 또는 드라이버 업그레이드 전 반드시 실제 합성 issuer 시험을 다시 실행한다.

Go 메모리 목표 `GOMEMLIMIT=96MiB`, `GOGC=25`는 합성 시험에서 추가 issuer로 인한
메모리 압박을 줄이기 위해 사용했다. 이는 hard RSS limit이나 지연 보장이 아니며,
운영 적용 시 기존 service memory limit도 보존한다. 이 조합의 실제 합성 issuer 시험은
코드 교환·연속 회전·중복 응답·재사용 폐기·캐시 거부를 통과했으나, 코드 교환 5.29초는
Gemini 시간 제한 안에 성공한다는 증거가 아니다. 앞선 제한 없는 두 시험은 timeout으로
실패했으며 완료로 계산하지 않는다. 운영 권한·token lifetime·회전·클라이언트 지침은
이 후보의 변경 대상이 아니다.

환경 override로 다시 실행한 합성 시험에서는 코드 교환이 7.61초 걸렸다. WAL만으로
실제 연결 기한을 만족한다고 판단하지 않으며 운영 전환은 보류한다. 실제 DB 경로는
바꾸지 않았고 운영 DB 저널도 전환하지 않았다.

검증기는 `--client-hash pbkdf2`로 합성 클라이언트에만 PBKDF2-SHA512 310000회를
사용하는 비교를 지원한다. 사용자 로그인용 Argon2는 유지한다. 이는
[Authelia의 OIDC 해시 비용 안내](https://www.authelia.com/integration/openid-connect/frequently-asked-questions/#tuning-work-factors)를
따른 시험이며, 운영 자격증명이나 해시를 자동 변경하는 기능이 아니다. 기본 DELETE
저널과의 합성 조합은 코드 교환 4.80초 및 갱신·폐기 검사를 통과했다. 단일 실행 시간은
NAS 부하의 영향을 받으므로 다른 조합보다 확실히 빠르다는 결론이나 실제 Google
시간 제한의 근거로 사용하지 않는다.

PBKDF2와 FULL WAL을 함께 사용한 합성 시험은 코드 교환 2.74초와 동일 갱신·폐기
검사를 통과했다. 운영 후보는 `client_secret_hash.py`로 기존 Argon2 해시와 현재
기계 자격증명의 일치를 먼저 확인한 뒤, 같은 문자열의 salted PBKDF2-SHA512
310000회 해시만 변경한다. 사용자 로그인용 비밀번호 해시, 클라이언트 ID, redirect,
scope, 토큰 수명은 변경하지 않는다. 이 해시 방식 변경은 운영 승인 대상에 명시한다.
실제 Authelia 바이너리로 Python 생성 합성 해시의 검증도 확인했다.

후보 전환은 issuer 및 해당 의존 서비스 정지, 보호 백업, 현재 DB 저널 전환, 정확히
한 클라이언트의 해시 변경과 service override, 기존 서비스 순서대로 시작, 원본 설정의
허용된 차이와 health 검사 순서다. 실패 시 기존 해시/환경 설정과 현재 DB의 DELETE
저널로 되돌린다. 원래 상태였던 의존 서비스도 다시 시작한다. Google의 실제 연결,
두 번의 실제 토큰 갱신과 지식 추가·재조회 전에는 운영 완료로 표시하지 않는다.

### 전환 시 갱신 서비스의 재시작

기존 listener는 `SO_REUSEADDR`를 사용하지 않아 health 요청 후 정지했을 때 남은
TIME_WAIT 소켓 때문에 같은 포트의 시작이 실패했다. NAS의 별도 합성 포트에서
`EADDRINUSE`를 재현했고 주소 재사용을 허용한 수정본의 즉시 재시작을 확인한다.
`SO_REUSEPORT`는 사용하지 않으며 실행 중 listener와의 중복 bind는 계속 거부한다.
재시작 시 토큰 캐시는 이전처럼 사라진다. 이 변경은 OAuth 판정·권한을 바꾸지 않는다.

재사용을 설정하지 않았던 구버전에서 처음 전환할 때는 구 소켓이 만료될 때까지
기다려야 할 수 있다. operator는 서비스 정지 확인 후 해당 loopback 포트의 bind를
최대 90초 검사한다. 다른 프로세스를 강제 종료하거나 점유한 포트를 빼앗지 않는다.
실패 복구 때도 원래 listener 설정에 맞춰 같은 검사를 수행한다.

## 병렬 인증 대기열과 실제 웹 검증 (2026-11-17)

`d439113`은 opaque 검증의 issuer 동시성 2를 유지하면서 총 8개 요청을 수용하고,
최대 6개를 worker에서 제한 시간 동안 기다리게 한다. 모든 요청은 slot을 얻은 뒤
새 introspection을 수행한다. 즉시 포화 거부를 줄이는 변경이며 비활성 토큰 허용이나
인증 결과 캐시가 아니다. 로컬 제품 시험 736개 통과·선택적 개인 연동 8개 생략,
CI 통과, 비공개 전환·복구 시뮬레이션 8개 통과 뒤 운영 활성화와 실행 소스를 확인했다.

검증 도중 정상 인증과 inactive/401이 함께 관측됐다. 후속 검증에서
introspection_unavailable/503도 한 번 관측됐지만 처리 시간은 10,014ms로 이전의
즉시 포화 거부와 다르다. 같은 구간 GPT health도 한 번 timeout 후 200으로 회복했다.
이를 인증 우회나 timeout 증가의 근거로 삼지 않는다. 갱신 발급과 소켓 쓰기 성공,
도구 목록 노출, 업무 실행, 저장, 별도 원문 조회, 웹 결과 표시는 각각 별도 증거다.
초기 성공이나 재시도 후 성공으로 실패한 새 채팅을 합격 처리하지 않는다. partial
결과를 전체 계좌의 최신성 확인으로 쓰지 않는다. 비공개 원문·계좌·로그·내부 경로는
이 공개 기록에 포함하지 않는다.

마지막 사례에서 모델은 메모를 찾지 못했다고 말하며 관련 없는 정책 문구를 제시했다.
그러나 해당 요청 구간에는 Knowledge 도구 호출이 없었다. 검색 결과가 없었다는
근거로 쓰거나 인증 실패만으로 설명하지 않는다. 별도로 소스상 `search_knowledge`는
현재 Claim 본문 등만 검색하고 연결된 Evidence 제목을 검색하지 않는다. 제목 검색의
구현 한계와 도구 미호출, 인증 오류는 서로 다른 실패 분류다.

## Google 실행 권한과 회전 호환성의 경계

Google의 App actions 확인은 OAuth scope와 NAS의 서버 승인과 별도다. 사용자가
명시적으로 허용한 경우에만 실제 조회 12개와 append-only `register_knowledge`의
Always allow를 비교할 수 있다. Read only 분류에는 preview 3개도 있으므로 범주를
일괄 변경하지 않는다. preview/apply 6개는 개별 확인을 유지한다. UI의 즉시 표시와
다시 열었을 때의 저장 상태를 대조한다. 실제 시험에서 조회 12개는 허용 표시가
유지됐으나 등록 도구의 표시는 되돌아갔고, 대화 내 항상 허용 뒤 등록 성공도 있었다.
등록 도구를 단독으로 다시 설정한 뒤 화면을 나갔다 들어와 13개 허용·6개 확인을
확인했다. 이 관측만으로 401 해결을 주장하지 않는다.

[Google MCP OAuth 가이드](https://developers.google.com/connected-apps/mcp/oauth)는
Persistent Linking에서 기존 refresh token 유지와 만료 연장을 안내한다.
[계정 해제 가이드](https://developers.google.com/identity/account-linking/unlinking)는
클러스터 동기화 전 이전/새 미만료 토큰이 함께 사용될 수 있다고 설명한다.
반면 고정한 [Authelia 4.39.28 schema](https://github.com/authelia/authelia/blob/v4.39.28/internal/configuration/schema/identity_providers.go)에는
`DisableRefreshTokenRotation`이 없다. master의 설정을 stable에 적용하지 않는다.
이는 현재 회전 계약과의 호환성 문제를 뒷받침하지만 모든 UI 실패를 설명하는
완전한 인과 추적은 아니다. 60초 동일 요청 중복 억제는 비회전·sliding 만료와 다르다.

기존 만료·회전·live 검증을 보존하는 이번 배포에 비회전, 수명 연장, 폐기 토큰 허용,
새 issuer를 추가하지 않았다. Google 권고를 이유로 이 보안 계약을 자동 변경하지
않는다. 서버 스케줄링과 운영 안내의 소유 변경이므로 공통 업무 지침·양쪽 생성
클라이언트 패키지·도구 스키마는 변경하지 않으며 재설치도 요구하지 않는다.
